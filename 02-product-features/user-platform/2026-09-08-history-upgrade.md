# 解读记录升级实施说明

日期：2026-09-08
状态：代码已实现，待执行 SQL 与部署。

## 本轮范围

- 保留八字／六爻分类；关键词搜索覆盖当前类型的所有记录。
- 默认使用较早的用户提问作为可读标题；用户可以手动修改。
- 展开摘要时按需生成标题、主题、问题摘要和历史解读要点。
- 原对话继续作为唯一事实源，摘要失败不会影响继续对话。
- 用户标题优先，摘要生成和修改标题不会改变历史会话排序。
- 新消息到来后标记摘要过期，由用户手动更新。
- 页面重新排版，手机单列，删除／清空收进管理菜单。

## 上线顺序

1. 选中应用 MySQL 数据库，运行后端 scripts/2026-09-08_conversation_digests.sql（首次迁移只执行一次）。
2. 部署后端，再部署前端。新版列表接口依赖新表，请勿跳过迁移。
3. 无需批量回填旧记录；首次展开摘要时生成并缓存。

SQL 根据 conversations.id 的实际字段类型创建外键，兼容历史数据库的 signed/unsigned 差异。
它创建 conversation_digests 并向 app_config 写入 history_digest_prompt，不覆盖已有同名配置。
提示词保存在数据库；缺少配置或模型不可用时显示可重试状态。

## 行为与限制

- 原有 DeepSeek 配置继续复用；额外摘要调用不扣用户解读次数。
- 每进程最多 2 个并发摘要调用；同记录请求间隔至少 60 秒。
- 每用户按最近一小时请求过的记录数限额 10 条，非精确累计调用账本。
- 最多读取最近 80 条消息，输入最多 24000 字符；界面明确摘要基于部分历史。
- 后台任务使用 FastAPI BackgroundTasks；进程退出可能中断，2 分钟后允许恢复重试。
- 摘要仅回顾历史，不自动注入新对话，不做结果回填、提醒、月报或年度报告。
- 搜索采用数据库 LIKE，较大数据量时应根据实际查询耗时再优化索引。
- 仍沿用现有会话类型判定；关联档案或卦象删除后的历史归属属于既有边界，未在此轮迁移历史数据。
