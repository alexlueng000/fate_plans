# 八字 Agent 产品与技术升级路线图

> 日期：2026-08-01  
> 适用范围：`fate_backend` 八字排盘、AI 解读、知识库、用户档案与评测体系

## 一、结论

当前系统已经具备“排盘 + 知识库检索 + 连续对话 + 消息持久化”的八字助手能力，但还不是完整意义上的八字 Agent。

现有主流程本质上是：

```text
用户问题
→ 检索少量知识片段
→ 拼接 System Prompt、命盘与最近对话
→ 大模型直接生成答案
```

真正的八字 Agent 应具备以下闭环：

```text
理解问题与分析对象
→ 检查资料完整性
→ 制定分析计划
→ 调用确定性命理工具
→ 检索适用规则
→ 形成候选判断
→ 检查矛盾与反证
→ 输出结论、依据、不确定性与现实建议
→ 保存可复用的分析状态
```

当前整体可视为已完成约 50%～60% 的产品和工程底座。下一阶段最重要的不是继续扩充 Prompt，而是建设“结构化命理推演引擎 + Agent 编排层 + 金标评测体系”。

## 二、现有能力

目前系统已经具备：

- 基于 `lunar-python` 的四柱和大运计算。
- 公历、农历出生日期输入。
- 基于经度的简化真太阳时修正。
- DeepSeek 流式对话。
- 命盘信息注入与本命盘锚点。
- 本地知识库向量检索。
- Redis/内存会话状态和数据库消息持久化。
- 用户档案、历史会话、点赞点踩与意见反馈。
- 基础内容过滤和娱乐参考提示。

这些能力足以支撑一个可用的八字聊天产品，但尚不足以保证命理计算的可追溯性、回答的一致性，以及复杂任务中的自主规划能力。

## 三、核心缺口

### 3.1 缺少确定性的命理推演引擎

当前排盘主要输出四柱和大运，后续大量判断仍交给大模型根据 Prompt 和知识片段完成。需要将可计算、可枚举的命理关系从大模型中剥离，改为确定性代码。

至少需要计算：

- 藏干、十神、十二长生、纳音。
- 天干五合及合化条件。
- 地支六合、三合、三会、六冲、刑、害、破、自刑。
- 月令、司令、通根、透干与根气。
- 五行力量，而不是简单统计八个干支的表层数量。
- 日主旺衰及判断依据。
- 格局候选、成格条件与破格条件。
- 调候、扶抑、通关、病药等取用路径。
- 喜神、用神、忌神及置信度。
- 原局、大运、流年、流月之间的作用关系。
- 合盘双方的关系矩阵。
- 神煞体系，如产品决定采用，应作为可配置的辅助层，而非核心判断层。

建议形成如下纯函数链路：

```text
排盘
→ 标准化命盘
→ 提取命盘特征
→ 生成旺衰/格局候选
→ 推导喜忌
→ 分析大运流年
→ 映射用户问题主题
→ 自洽性检查
```

原则是：代码负责计算，规则引擎负责推导，大模型负责解释、组织和对话。

### 3.2 历法与真太阳时仍不完整

当前真太阳时主要采用“经度差 × 4 分钟”的简化方法。正式产品还需要处理：

- 均时差（Equation of Time）。
- 出生地所属时区。
- 海外出生地及历史时区变更。
- 中国历史夏令时。
- 子初换日与子正换日的流派配置。
- 早子时、晚子时规则。
- 农历闰月输入与明确标记。
- 节气交界前后的秒级边界。
- 出生时间不确定时的候选时柱。
- 地理编码失败时明确告知用户，不能静默退回本地时间。

建议把排盘配置显式保存：

```json
{
  "timezone": "Asia/Shanghai",
  "longitude": 113.27,
  "true_solar_time": true,
  "equation_of_time": true,
  "day_boundary_rule": "23:00",
  "calendar": "gregorian",
  "leap_month": false,
  "calculation_version": "bazi-engine-1.0"
}
```

同一份出生资料在任何时间重新计算，都应能得到相同结果并知道采用了哪套规则。

### 3.3 缺少 Agent 编排层

当前系统是单轮检索后直接调用模型。需要增加显式的任务分类、计划、工具调用和验证流程。

建议提供以下 Agent 工具：

- `calculate_chart`：计算并标准化命盘。
- `extract_chart_features`：生成十神、藏干及各种关系。
- `analyze_strength`：给出旺衰候选和证据。
- `derive_useful_elements`：生成喜用忌候选和推导路径。
- `analyze_dayun`：分析指定大运。
- `analyze_liunian`：分析指定年份或年份区间。
- `compare_charts`：合盘和人物关系分析。
- `get_current_ganzhi`：获取当前年月日时干支。
- `search_bazi_knowledge`：检索符合主题和流派的规则。
- `validate_conclusion`：检查结论与计算结果是否矛盾。

建议引入有限状态机，而不是让模型无限自主循环：

```text
INTAKE
→ CLARIFY
→ PLAN
→ CALCULATE
→ RETRIEVE
→ REASON
→ VERIFY
→ RESPOND
→ PERSIST
```

每次运行应保存：

- 任务类型。
- 分析对象。
- 使用的命盘版本。
- 工具调用及结果摘要。
- 使用的规则来源。
- 最终结论和置信度。
- 失败、降级和重试情况。

### 3.4 命理结论缺少证据链

目前知识库以向量相似度取 Top-K 文本，缺少规则级元数据和冲突处理。需要把知识库从“文档片段集合”升级成“可治理的命理规则库”。

每条规则建议包含：

- 规则 ID。
- 流派和来源。
- 规则正文。
- 适用条件。
- 排除条件。
- 优先级。
- 反例或争议说明。
- 专家审核状态。
- 版本和更新时间。

检索应升级为：

```text
主题/流派过滤
→ 关键词与向量混合检索
→ Reranker 重排
→ 适用条件过滤
→ 冲突规则仲裁
```

内部判断建议采用结构化格式：

```json
{
  "claim": "当前大运事业变动性增强",
  "confidence": "medium",
  "evidence": [
    "大运地支冲原局月支",
    "官杀在流年透干"
  ],
  "counter_evidence": [
    "原局存在印星通关"
  ],
  "rule_sources": ["rule_102", "rule_284"]
}
```

用户界面可以只展示简化依据，但系统内部必须保留完整证据链。

当前知识库索引中存在非命理文件内容，例如依赖清单，说明索引构建需要增加文件白名单、内容校验和发布门禁。

### 3.5 长期记忆与人物管理不足

最近若干条聊天记录不等于 Agent 记忆。需要区分：

- 永久事实：出生资料、本人命盘、排盘配置。
- 人物档案：本人、伴侣、家人、合作对象。
- 已确认事件：结婚、转职、搬迁等实际年份。
- 历史判断：过去给出的结论和依据。
- 当前任务状态：正在分析的对象、年份和主题。
- 用户偏好：表达风格、是否展示专业术语。
- 待验证假设：出生时辰是否准确、某事件是否发生。

建议增加核心数据模型：

```text
Person
Chart
ChartCalculationVersion
AnalysisCase
AgentRun
ToolCall
Evidence
Conclusion
VerifiedLifeEvent
```

多个命盘不能仅依赖 Prompt 中的“本命盘锚点”防止混淆，必须通过 `person_id`、`chart_id` 和 `analysis_case_id` 隔离。

### 3.6 缺少问诊式任务澄清

真正的 Agent 不应收到任何问题都立刻生成长篇命理判断。它需要先确认：

- 分析本人还是他人。
- 任务属于原局、流年、合盘、择时还是事件验证。
- 出生时间是否确定。
- “今年”“最近”等相对时间具体指哪一年。
- 用户要趋势判断、候选比较还是行动建议。
- 是否缺少性别、出生地、时区等关键数据。

例如“今年适合换工作吗”应拆解为：

1. 确认当前年份和分析对象。
2. 获取当前大运及当年流年。
3. 判断与事业相关的命理作用。
4. 收集候选岗位、现金流和风险承受能力等现实约束。
5. 输出命理倾向、现实检查项和决策建议。

### 3.7 缺少专业评测体系

需要建立以下评测集：

#### 排盘金标集

- 立春及其他节气交界。
- 23:00～01:00 子时边界。
- 农历闰月。
- 中国历史夏令时。
- 海外时区和跨日期边界。
- 真太阳时造成时柱变化的案例。

#### 命理规则金标集

- 十神、藏干。
- 合冲刑害破。
- 三合、三会及合化条件。
- 旺衰、格局和喜忌。
- 原局、大运、流年组合关系。

#### 对话任务集

- 事业、婚恋、财运、学业。
- 合盘、多人物切换。
- 出生时间不确定。
- 用户用现实经历验证结论。
- 追问后保持前后一致。

#### 安全集

- 健康和疾病。
- 投资和负债。
- 死亡、灾祸及法律风险。
- 婚姻、离职等重大人生决定。
- 心理危机和过度依赖。

核心指标包括：

- 排盘一致率。
- 工具调用正确率。
- 规则引用正确率。
- 命盘人物混淆率。
- 前后回答一致率。
- 无依据断言率。
- 高风险回答违规率。
- 专家盲评通过率。
- 用户事实验证率。

点赞、点踩只能作为弱反馈，不能代替金标评测和专家审核。

### 3.8 安全边界需要进入推理流程

“仅供娱乐参考”不能只作为文末免责声明。Agent 应在生成结论前识别风险：

- 不预测具体死亡、重病或必然灾难。
- 不把命理分析当作医疗诊断。
- 不提供确定性的投资买卖指令。
- 不鼓励仅凭八字决定结婚、离婚、辞职或借贷。
- 遇到心理危机时优先提供现实支持和求助渠道。
- 明确区分命理倾向、现实事实和行动建议。

建议输出分层：

```text
命理观察
→ 不确定性
→ 现实验证项
→ 低风险行动建议
```

## 四、建议目标架构

```text
Web / App / 微信小程序
        ↓
Agent API
        ↓
任务识别与状态机
        ├── 人物与命盘服务
        ├── 历法排盘引擎
        ├── 命盘特征引擎
        ├── 旺衰/格局/喜忌引擎
        ├── 大运流年引擎
        ├── 合盘引擎
        ├── 规则知识库与检索
        ├── 结论验证器
        └── 安全策略引擎
                ↓
          大模型表达层
                ↓
      结论、依据、置信度、建议
                ↓
      Agent Run / Evidence 持久化
```

大模型不应直接修改命盘或生成不可验证的中间计算结果。所有关键命理事实均由工具产生，并以结构化数据传给模型。

## 五、分阶段实施路线

### 第一阶段：算得对

目标：建立可信、可回归的确定性命理底座。

1. 定义统一 `BaziChart` Schema 和计算版本。
2. 完善时区、真太阳时、节气和子时边界。
3. 实现藏干、十神、十二长生、合冲刑害破。
4. 实现五行力量、旺衰和喜忌候选计算。
5. 建立 200～500 个排盘及基础规则金标案例。
6. 删除或隔离 demo 排盘逻辑。
7. 为每个确定性函数增加单元测试和边界测试。

验收标准：

- 核心排盘金标一致率达到 100%。
- 基础关系计算准确率达到 100%。
- 同一输入在相同计算版本下结果完全一致。
- 任何时间、地理编码或历法降级都显式返回警告。

### 第二阶段：想得清楚

目标：从 RAG Chatbot 升级为可规划、可调用工具、可验证的 Agent。

1. 增加任务分类器和分析对象识别。
2. 建立有限状态机及 Agent Run 数据模型。
3. 封装命理工具并支持结构化调用。
4. 增加结论、证据、反证和置信度结构。
5. 增加结论验证器，阻止命盘事实冲突。
6. 支持多人物、多命盘和合盘任务。
7. 对复杂问题支持必要的澄清提问。

验收标准：

- 所有关键命理事实来自工具结果。
- 可以完整回放一次回答使用了哪些工具和规则。
- 多人物命盘混淆率低于 1%。
- 同类问题重复回答的核心结论保持一致。

### 第三阶段：说得可信

目标：建设可治理的知识库和稳定的专业表达。

1. 重构知识库文件白名单和索引流水线。
2. 建立规则级元数据、版本和专家审核机制。
3. 使用混合检索、Reranker 和适用条件过滤。
4. 建立不同流派的配置和冲突仲裁规则。
5. 回答中提供简化依据和不确定性。
6. 建立专家审核后台和错误案例回流。

验收标准：

- 知识库不包含依赖文件等无关内容。
- 关键结论能够追溯到计算结果和规则来源。
- 无来源、无依据的确定性断言显著下降。

### 第四阶段：持续进化

目标：建立数据、评测和产品反馈闭环。

1. 上线自动回归评测流水线。
2. 将点踩原因映射到具体 Agent Run 和证据链。
3. 引入用户已验证人生事件，但不直接作为命理真理。
4. 建立专家抽检和版本对比机制。
5. 监控成本、延迟、工具失败率和安全违规率。
6. 对不同 Prompt、模型、检索和规则版本进行离线评测后再发布。

## 六、建议优先级

### P0：首先完成

- 统一命盘 Schema 和计算版本。
- 真太阳时、时区、节气边界和失败告警。
- 十神、藏干、合冲刑害破确定性计算。
- 排盘和规则金标测试集。
- 清理知识库污染。

### P1：Agent 核心

- 任务分类和状态机。
- 工具调用协议。
- 证据链和结论验证器。
- 多人物、多命盘数据模型。
- 大运流年分析工具。

### P2：专业化与规模化

- 旺衰、格局、喜忌多候选推导。
- 流派管理和规则冲突处理。
- 混合检索与 Reranker。
- 专家审核后台。
- 自动评测和发布门禁。

### P3：高级能力

- 出生时辰校验。
- 合盘和多方关系分析。
- 流月、流日和择时。
- 个性化长期建议与周期复盘。

## 七、推荐的第一期开发包

如果只开展一期，建议范围控制在：

1. `BaziChart` 标准数据结构。
2. 排盘计算版本化。
3. 完整十神、藏干、合冲刑害破工具。
4. 真太阳时和时间边界修正。
5. 300 个金标案例。
6. `AgentRun + ToolCall + Evidence + Conclusion` 数据结构。
7. 一个有限状态机，先支持“原局分析”和“三年事业趋势”两个任务。

这一期完成后，系统才具备真正八字 Agent 的最小闭环：

```text
用户提出问题
→ Agent 选择任务
→ 工具完成确定性计算
→ 规则库提供适用依据
→ 验证器检查矛盾
→ 模型组织自然语言答案
→ 保存全过程供评测和复盘
```

## 八、产品原则

- 算法可以确定的内容，不交给大模型猜。
- 命理观点必须带适用条件，不把单条口诀当绝对事实。
- 结论同时保留证据、反证和不确定性。
- 重大人生选择必须结合现实条件，不输出宿命式指令。
- 用户反馈用于发现问题，金标和专家审核用于判断对错。
- 每次计算和回答都应可追溯、可复现、可评测。

最终目标不是让 AI “说得更像大师”，而是让它能够稳定完成：正确排盘、结构化分析、证据化推理、连续任务管理和负责任表达。
